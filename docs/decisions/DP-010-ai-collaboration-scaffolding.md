# DP-010. In-repo AI collaboration scaffolding, and repair of stale AI-role documents

## 1. The question

An audit of the repository's existing AI-collaboration mechanisms (session of 2026-08-14, on
request) found a working decision/evidence memory (`docs/DECISION_LOG.md`, `docs/OPEN_QUESTIONS.md`)
but a thin, stale and inconsistent layer defining *how an AI collaborator is supposed to behave*, and
no in-repo, tool-readable bootstrap file at all.

Should the repository adopt a `CLAUDE.md`-centered AI-tooling layer, what should it contain, and
should it be paired with `.claude/skills/` for repeatable procedures? Separately, several existing
documents in this space are stale or inconsistent and need a repair decision regardless of the answer
to the first question.

**This paper decides nothing.** No file described here is created, and no stale document is repaired,
without owner approval.

## 2. What the audit found, and why it cannot be left as-is

**The authoritative AI-role document is stale relative to its own repository.**
`docs/PROJECT_CONSTITUTION.md` s11 ("AI Collaboration Model") is the only place the two-AI
architecture is actually defined: ChatGPT as reviewer/auditor, Claude as builder/executor, the owner
ratifying all decisions. The whole constitution is still `Status: DRAFT, Version 0.1.0, Last updated
2026-07-11` — before Q1 named an owner, before Tier-0 locked, before ADR-0042 established the
authority hierarchy that names this very document as senior to `engineering/ENGINEERING_CONSTITUTION.md`.
That subordinate document's own AI clause (Principle 11: "every implementation generated by AI must
be reviewed before entering Git") is marked `Status: ACTIVE`, so the senior document in the hierarchy
carries the junior status label. This is the same defect class `docs/OPEN_QUESTIONS.md` Q21 and
ADR-0042 exist to prevent, just not yet caught for this pair.

**The operational detail sits in an unstatused document.** `specs/CLAUDE_WORKFLOW.md` describes the
handoff-package pattern (spec freeze, package, implement, audit, lock) underneath s11, but carries no
status header, version, or owner field at all, contrary to `docs/DOCUMENTATION_STANDARD.md` s2's
mandatory structure for governing documents.

**No in-repo bootstrap file exists.** There is no `CLAUDE.md` anywhere in the repository, no
`.claude/skills/`, `.claude/agents/`, or `.claude/commands/`, and no `AGENTS.md` or equivalent. The
`.claude/` directory that does exist on this machine (`settings.json`, `settings.local.json`) is
**untracked** — never committed, not gitignored, just never staged — so it is invisible to a fresh
clone and to any other collaborator or tool. The audit-first, evidence-over-narrative,
never-self-certify, never-weaken-a-gate discipline that every session in this repository's history has
in fact followed currently lives only in prose scattered across half a dozen governing documents, and,
for at least one AI tool in current use, in a per-session external prompt that is not part of the
repository at all. `reports/REPOSITORY_AUDIT_REPORT.md` cites "PROJECT_CONSTITUTION.md FIRST TASK" as
the authority for its own audit-first method; no such section exists in the constitution as written,
which is itself an instance of the citation-drift defect class this project's audits already track
(`docs/DECISION_LOG.md` L-8).

**One AI-role-adjacent document is stale in a way that actively misleads, not merely historically.**
`docs/PROJECT_MASTER.md` describes a Flutter-app pipeline and an `app/` top-level folder. ADR-0041
(2026-08-14) explicitly excludes `app/` from the canonical top-level structure, and the document
predates the multi-domain Jyotisha pivot (ADR-0019, ADR-0020) entirely. Unlike the other stale
root-level documents (`FINAL_CERTIFICATION_REPORT.md`, `FINDINGS_MATRIX.md`, `REMEDIATION_SUMMARY.md`,
`TEST_RESULTS.md`), which each carry an explicit `SUPERSEDING NOTE` pointing to current truth, this one
carries none. A cold AI session reading it first would form a wrong architectural model with no warning.

**The cross-session handoff convention is real but undocumented.** Git bundles and diffs
(`ace-*.bundle`, `*.patch`) are used to hand state to the CEO/ChatGPT for review — referenced once,
informally, in `HOLD_REMEDIATION_PROPOSALS.md` — but named in no standard, not gitignored, and not
cleaned up (eleven such files currently untracked in the repository root). Separately,
`reports/REPOSITORY_AUDIT_REPORT.md` references a `MASTER_HANDOFF.md` that does not exist anywhere in
the repository or its history: evidence that an earlier ad hoc handoff package was used once, in a
one-off cloud audit container, and left no reproducible trace in-repo.

## 3. A constraint that shapes every option below

Whatever is written must not duplicate normative content that already lives in
`docs/PROJECT_CONSTITUTION.md`, on pain of recreating exactly the drift already found between that
document and `engineering/ENGINEERING_CONSTITUTION.md`. `docs/DOCUMENTATION_STANDARD.md`'s own
lifecycle rule (`RATIFIED documents change only alongside a decision log entry`) and ADR-0042's rule
(`an ADR does not itself narrow a higher-level constitution or standard`) both point the same
direction: a tool-specific bootstrap file should **operationalize** the constitution, not **restate**
it as a second source of truth that can silently diverge.

## 4. Options for the CLAUDE.md question

**Option A. Thin pointer only.** `CLAUDE.md` contains no restated policy, only an ordered reading list
(`PROJECT_CONSTITUTION.md`, `DECISION_LOG.md`, `OPEN_QUESTIONS.md`, `CLAUDE_WORKFLOW.md`, `README.md`)
and instructs the collaborator to derive behaviour from those. Zero duplication risk, by construction.
Costly in practice: tools that skim or summarize context tend not to follow multi-hop pointers with
the same fidelity as inline instructions, and this repository's governing documents are long enough
(the decision log alone is 2,300+ lines) that "go read everything" is a weak substitute for a stated
summary of the load-bearing rules.

**Option B. Operational restatement, explicitly cited.** `CLAUDE.md` states the load-bearing rules
actionably (mandatory state audit before any change, evidence over narrative, no self-certification,
never weaken a gate to obtain green CI, owner ratifies all decisions, stop conditions, completion-report
format) with each clause citing the constitution section or spec it derives from, the same discipline
`VALIDATION_STANDARD.md` already requires of certification claims. Duplication is real but bounded and
traceable: a future audit can mechanically check that every cited section still says what `CLAUDE.md`
claims it says, the same way `scripts/check_artifact_drift.py` already checks a narrower claim.
Requires a keep-in-sync discipline (see section 6) that does not yet have a mechanical gate.

**Option C. CLAUDE.md as the new source of truth, s11 reduced to a pointer.** Inverts today's
direction: the constitution's AI-collaboration section becomes a one-line reference to `CLAUDE.md`,
which becomes authoritative. Rejected reasoning stated because the option is real: this would place
the project's constitutional layer partly inside a tool-specific file format that not every AI
collaborator's tooling reads by convention, and ADR-0042's authority hierarchy places the constitution
above tooling, not the reverse. Downgrading it would need its own ADR, not a documentation paper.

**Option D. Defer CLAUDE.md and skills; repair only the existing documents.** Ratify or at least
version-sync s11, add a status header to `CLAUDE_WORKFLOW.md`, add a superseding note (or retire)
`PROJECT_MASTER.md`, name the transfer-bundle convention in `NAMING_STANDARD.md` or retire it. Leaves
the audit-first discipline dependent on per-session external prompts for any tool that supplies one,
and undiscoverable for any tool or session that does not. Cheapest option; does not close the gap the
audit found, only the staleness.

## 5. Options for `.claude/skills/`

**Option E. No skills; scaffolding is `CLAUDE.md` only.** Simplest. The repeatable procedures already
observed in this repository's history (mandatory state audit, ADR authoring against
`scripts/check_adr_numbering.py`, the independent-audit-blind-to-conclusions method described in
`reports/PHASE_G_GOVERNANCE_AUDIT_2026-08-13.md` s1, the transfer-bundle handoff) stay as prose,
followed by convention rather than invoked as a packaged procedure.

**Option F. A small, named set of skills for the procedures already proven in this repository's own
history.** Candidates: a state-audit skill (the mandatory-audit checklist this paper's own producing
session followed), a decision-entry-authoring skill (numbering, status header, evidence citation format), and a
handoff skill (formalizing the transfer-bundle convention into something reproducible and cleaned up
automatically, closing the `MASTER_HANDOFF.md`-left-no-trace gap from section 2). Makes the procedures
executable rather than merely documented, at the cost of a second thing (skills) that can drift from
the prose describing the same procedure if not kept in sync.

## 6. Recommendation

**Option B for `CLAUDE.md`, Option F for skills, both narrow at first.** Confidence: medium-high on B,
medium on F.

B is recommended over A because a purely-pointer file has already been tried, in effect: the
governing documents already exist and already say all of this, and the audit that produced this paper
found the discipline followed in practice but not durably encoded for a cold session or a different
tool. B is recommended over C because C requires re-litigating ADR-0042's hierarchy, which this paper
should not do quietly. B's duplication risk is real but is the same shape of risk
`VALIDATION_STANDARD.md` already manages for certification claims: cited, bounded, and auditable,
which is a materially different risk profile from silent restatement.

F is recommended over E at medium rather than high confidence, because the third candidate skill
(handoff) requires deciding what replaces or formalizes the transfer-bundle convention, which is a
narrower question this paper has not fully explored and which the owner may prefer to defer
independently of the `CLAUDE.md` decision.

I recommend against Option D standing alone: repairing the stale documents without also closing the
durability gap leaves the next cold session, or a differently configured one, exactly where the
producing session started — reconstructing the discipline from scattered prose with no in-repo
guarantee.

## 7. What the decision must also settle, whichever option is chosen

Whether `.claude/` becomes tracked in git at all (it is currently untracked; if it should be, the two
existing narrow permission files need review, since `settings.local.json` currently contains
session-specific leftovers rather than authored policy). The keep-in-sync mechanism for Option B's
citations: manual discipline, a periodic audit, or a mechanical gate modeled on
`scripts/check_artifact_drift.py`. Whether `docs/PROJECT_CONSTITUTION.md` s11 is ratified as part of
this decision or separately, since `CLAUDE.md` would cite it either way and a DRAFT citation is weaker
evidence than a RATIFIED one. The disposition of `docs/PROJECT_MASTER.md` (superseding note versus
retirement, matching the pattern already used for the other stale root documents). Whether the
transfer-bundle convention is formalized, replaced, or retired, and what happens to the eleven
currently-untracked bundle files in the repository root. And whether this paper's own scope should
have been narrower, given it bundles a tooling decision with several document-repair decisions that
could in principle be ratified independently.
